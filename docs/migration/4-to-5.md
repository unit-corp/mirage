# Migrating from Mirage-SQL 4.x to 5.x

## Status

This guide defines the controlled migration to release `5.0.0`. The release uses groupId `vn.com.unit.miragesql`, standard artifact names without `-legacy`, Java package `vn.com.unit.miragesql`, Java 17, and the Spring Boot 4 dependency-management baseline.

Do not approve a production upgrade until the target tag, published artifacts, breaking-change inventory, and verification results are available.

## Source baseline

The verified `4.x` source has two layouts:

- `legacy-v4.0.1` and `maintenance/legacy` use groupId `vn.com.unit.miragesql`, `-legacy` artifact suffixes, and Java package `com.miragesql`.
- Release `5.0.0` uses artifact names without `-legacy` and Java package `vn.com.unit.miragesql`.

Both inspected source variants require Java 17 and are built against Spring Boot 4. See [Compatibility](../../COMPATIBILITY.md) for the module mapping.

## Migration procedure

### 1. Record the current variant

Capture the dependency tree and determine whether the application uses the legacy-package or renamed-package `4.x` variant. Check source imports and string-based class references in Spring XML, configuration, reflection, and serialization metadata.

```bash
mvn dependency:tree -Dincludes=vn.com.unit.miragesql
```

Do not proceed while both variants are present in the same application.

### 2. Confirm the target release

Before editing the application, replace this section with values verified from the target `5.x` tag and POMs:

- release tag and commit
- groupId, artifactIds, and version
- Java package
- minimum Java version
- Spring and Jakarta baselines
- supported database and JDBC-driver matrix
- removed, renamed, or behaviorally changed APIs
- publication location and checksums or signatures where applicable

### 3. Update dependencies

Update every Mirage-SQL module to the same target version. Exclude transitive `4.x` artifacts and verify that the resolved dependency tree contains only one line. Do not assume that the `4.x` artifact names remain valid in `5.x` until the target POMs confirm them.

### 4. Apply code and configuration changes

Use compiler errors and the confirmed breaking-change inventory to update imports, public API usage, connection providers, session lifecycle, transaction integration, dialect configuration, stored-procedure calls, and custom extensions.

Search configuration separately because class names stored as strings are not validated by the compiler:

```bash
rg 'com\.miragesql|vn\.com\.unit\.miragesql' src
```

### 5. Verify behavior

At minimum, verify:

- Maven build and all module tests
- application startup and shutdown
- transaction commit and rollback paths
- connection acquisition, release, and pool exhaustion behavior
- dynamic SQL conditions and bind variables
- CRUD, generated keys, pagination, batch operations, and stored procedures used by the application
- database-specific types, identifiers, quoting, and error handling
- concurrent workload and representative performance

### 6. Roll out and roll back

Deploy through the application's normal staged rollout. Monitor SQL errors, connection-pool metrics, transaction failures, latency, and database load. Rollback means restoring the previous application artifact and dependency set. Any application-owned schema or data change needs its own backward-compatible rollback plan.

## Release-readiness gate for this guide

This guide is ready to remove its draft warning only when all target facts above are sourced from a `5.x` tag or immutable release commit, the artifacts can be resolved from the documented repository, automated tests pass, and the breaking-change inventory has been reviewed against the public API.
